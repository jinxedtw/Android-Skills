# 修 Bug

先定位、后修改。证据不足时不要断言根因，也不要大改代码。

## 何时使用

用户提到或表达：

- 修 bug
- 找原因
- 处理问题
- 解决问题

或描述「某功能异常 / 测试正常正式失效 / 无法稳定复现」等。

## 工作流程

### 1. 先描述 Bug（必须）

开场先用自己的话写清 bug 是什么，至少包含：

- **现象**：用户看到/感觉到什么
- **期望**：本应怎样
- **范围**：哪个功能、哪个环境（如 debug/release、机型、系统版本）

用户没讲清时，先问，不要直接改代码。

### 2. 要稳定复现（用户没给就要追问）

若用户**没有**给出可稳定复现的步骤或测试用例，必须先向用户要，例如：

- 逐步操作路径（从哪进、点什么、等多久）
- 前置条件（权限、登录态、数据、网络）
- 环境差异（debug 包 vs release 包、测试机 vs 正式机）
- 出现频率（必现 / 偶现；偶现时的规律）

可请用户补充成简短「测试用例」或「复现流程」。没有稳定复现前，只做只读排查与提问，不做功能性修复提交。

### 3. 收集证据，再谈原因

按优先级收集：

1. 相关代码路径与调用链
2. 测试/正式（或 debug/release）行为差异
3. 日志：关键节点前后完整相关日志（不要只有「开始」，没有「执行/失败」）
4. 能区分失败阶段的信号（例如：任务是否入队、是否触发、触发后是否执行失败）

用证据区分：

- **没触发**（调度/入口/权限/被取消）
- **触发了但执行失败**（中途 return、异常、依赖未就绪）
- **执行了但用户感知失败**（UI/副作用没出现）

证据不足时：列出待确认问题，问用户；不要猜完就改。

### 4. 不确定先问，再改

以下情况先问用户再动代码：

- 根因有多种可能，改法差异大
- 需要换实现方案（如换调度框架、改权限模型）
- 可能影响其它功能或数据

可以做的只读动作：搜代码、对比配置、解读日志、提出验证实验。

### 5. 修复与验证

- 改动对准已确认根因，避免顺手重构
- 给出**如何验证**的步骤（对应复现流程；含正式/release 若相关）
- 用户确认通过后，**仅在用户明确要求时**再 commit；不要擅自 push

## 输出格式

排查与沟通时默认用下面结构（可按进度删减）：

```markdown
## 已确认事实
- ...

## Bug 描述
- 现象：
- 期望：
- 范围：

## 复现 / 测试用例
- （用户已提供则原样整理；未提供则明确「待用户补充」）

## 待确认问题
1. ...

## 可能原因（按证据排序）
1. ... — 依据：...
2. ... — 依据：...

## 建议下一步
- 问用户 / 要日志 / 做只读验证 / 在确认后改代码
```

开始改代码时，简要说明：改什么、为什么、怎么测。

## 注意事项

- 不要在只有「设置成功」类日志、没有「执行」类日志时，就断言执行链路没问题
- 不要把偶现问题当成已修复，除非验证步骤覆盖原复现条件
- debug 正常、release 失败时，优先核对 minify、权限、后台限制、进程冷启动、构建类型差异，而不是先改业务逻辑
